# 园邻开发范围与推进计划

## 已确认范围

实际经营和本地演示均按一家门店设置。客户、门店员工、平台管理员三种角色；洗护与家政两条业务线都纳入目标范围。按“共享基础 → 两类服务完整流程 → 云端联调 → 小范围试运营”的顺序推进，每阶段都交付可体验版本。

## 阶段 0：先验收现有骨架（当前）

交付：本地演示、五个身份、一家门店、聊天与客户分页数据、模拟新客注册、数据重置。

通过条件：按《本地演示与功能验收》完成三角色操作，记录现有问题与缺失入口。自动测试通过和用户操作验收分别记录，不互相替代。

## 阶段 1：建立两类服务共用的交易基础

交付：
- 管理端服务目录、规格、门店服务范围、启停和展示。
- 客户服务详情、地址和联系人。
- 服务端计算金额，使用整数分；订单保存购买时服务和价格快照。
- 订单列表、详情、状态变更与操作记录；客户端不能自行指定可信金额或终态。

通过条件：客户可提交可履约的订单，所属门店可看到并受权限约束地处理，管理员能追溯。支付接入前明确使用测试流程，不显示真实已支付。

## 阶段 2：补齐洗护和家政各自的完整流程

### 洗护

服务选择 → 衣物清单/计价 → 取送方式与时间 → 下单 → 门店接单 → 收件确认 → 洗护处理 → 交付 → 完成。

需要明确：按件还是按重量计价、到店与上门范围、起送要求、验衣后是否允许改价、预计时效、异常衣物和赔付处理。

### 家政

服务选择 → 服务地址和时长 → 预约时间 → 下单 → 门店确认 → 分配人员 → 上门服务 → 完成确认。

需要明确：套餐/小时计价、服务区域、时间段容量、人员安排、临时改期与取消、超时费用和服务验收。

两类服务共用账户、门店、订单和交易能力；履约字段与状态分别设计。两条业务线都需要能走完正常路径和取消/失败路径，才算完成本阶段。

## 阶段 3：接通真实交易与异常处理

交付：微信支付与回调、支付前后取消规则、退款和对账、订单并发与幂等、缺货/无法履约/客户失联/改期等异常处理、必要的订阅提醒和售后记录。

通过条件：支付结果以服务端可信回调为准；重复回调不重复入账；支付失败不误显示成功；取消、退款及状态变更能追溯。

## 阶段 4：测试云环境与真机验收

先核对 AppID 和云环境，再验证：
- 真实注册登录与隐私授权；客户、一家门店及管理员多设备使用。
- 数据库权限、客户隐私隔离、会话撤销、并发提交、断网重试。
- 洗护和家政从创建到交付、取消、退款的完整流程。
- 入口码、订阅消息、生产配置、日志与恢复方案。

通过条件：关键故障和权限问题关闭，金额与履约状态一致，两条业务线分别通过验收。

## 阶段 5：本店小范围试运营

先使用少量真实订单验证取送、排班、服务时效、售后和人工处理能力。根据真实反馈排优先级，再考虑优惠券、会员、评价、营销、经营看板等扩展。

## 每次迭代的交付约定

1. 选定一个具体用户流程，并写出正常及失败时应有的结果。
2. 实现页面、接口、权限与必要的数据结构，更新演示。
3. 运行相称的自动测试，完成真机或演示验收。
4. 更新 CHANGELOG、已知缺口和验收结果；形成一个 Git commit。
5. 评审后推进下一流程；涉及云端发布时核对目标环境。

目前项目仅初始化 Git，尚无提交。首次提交应作为当前完整源码基线，之后按可验收的小功能分别提交。

## 后续需要业务确认的内容

两类服务的收费方式、服务区域、门店与人员职责、时效承诺、取消退款规则，以及首批实际服务项目。这些决定具体业务设计，应在对应阶段实现前确认。当前先完成角色体验，不需要一次列出所有细节。
