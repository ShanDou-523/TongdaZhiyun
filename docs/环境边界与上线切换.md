# 环境边界与上线切换

## 三种环境的分工

| 环境 | 用途 | 数据边界 |
|---|---|---|
| 本地演示 | 看页面、切换角色、快速回归 | 当前设备假数据，不证明多人或云端正常 |
| 个人开发云环境 | 真实数据库、CRUD、权限、多人聊天、订单业务联调 | 仅测试数据；现有数据性质和同事使用状态仍待确认 |
| 公司环境 | 最终 AppID 能力联调、验收、正式经营 | 正式身份和业务数据；建议测试与生产分开 |

可以立即开发客户/员工管理、服务CRUD、计价、洗护取送、家政预约排班、订单、取消退款规则、日志及权限。微信手机号、真实支付退款等平台能力可先封装和模拟，但须用符合条件的公司账号及商户配置完成真实验收。

开发登录不是修改前端角色。联调时必须验证服务端开关、测试人员范围、OpenID绑定和会话撤销；不能假定同一个微信随意更换测试手机号就能切换独立账号。

## 当前只读检查工具

`config/deployment-targets.json` 记录预期目标，并不切换前端或云端。开发目标来自交接说明；公司目标留空，等待真实信息，不填假 AppID。

```powershell
npm run env:check:dev
npm run env:check:prod
```

检查只读取本地文件，不联网、不修改配置、不部署、不触碰数据库。正式目标缺失、cloudEnv不匹配、AppID冲突、演示/开发登录开关未关、隐私配置为空，会给出明确提示；生产阻断项使进程退出码为1。

当前共享 project.config.json 与私有 project.private.config.json 的AppID不同。开发检查给出提示，实际运行身份必须在开发者工具中核实，脚本不会猜测覆盖优先级。正式检查要求配置一致。

即使本地检查通过，也不表示允许上线。云端真实环境变量、部署版本、资源归属、索引权限和支付能力仍是待验收项。当前工具未接入部署流水线，也不会阻止人在开发者工具里手动上传；自动部署和强制发布检查待源码对齐后实施。

## 最省迁移成本的约定

1. 个人云环境不承载真实收费运营，不积累需要迁移的真实余额、支付订单或正式客户。
2. 公司环境从干净业务数据开始：部署代码，创建集合/索引/权限，导入审核过的门店、服务、价格等经营配置。
3. 不复制测试用户、phoneClaims、会话令牌、聊天、订单和测试管理员身份。员工和客户在新AppID下重新建立身份，管理员重新核验初始化。
4. 新环境的云存储文件重新上传并更新引用；公司AppID下重新生成入口码、配置订阅模板，不复用个人AppID生成的码或OpenID。
5. 经营配置与演示种子分别管理。初始化须可重复执行且不会覆盖已有正式资料。
6. 私钥、AppSecret、支付密钥只存服务端或受控凭据服务，不进前端和仓库。

## 公司环境上线顺序

1. 公司确认小程序主体与认证、服务类目、必要备案和资质，老板授权开发成员；确认公司云账号、计费和资源归属。
2. 提供公司AppID与环境ID，按实际业务申请手机号、支付等能力，完成商户号绑定。无需等全部代码开发完才开始这些申请。
3. 先建立公司测试环境/体验版，部署经过整合且有提交号的代码。逐项恢复集合、权限、索引、云函数权限和必要配置。
4. 关闭所有开发登录与演示入口，核对云端DEV_LOGIN等真实设置；不要照抄个人环境变量。核验完初始管理员后撤销临时初始化配置。
5. 用真实账号完成注册、角色、消息、洗护与家政流程及支付退款验收；验证失败、并发和重试路径。
6. 导入正式经营配置，检查云存储引用、入口码、通知模板、隐私主体与联系方式、告警和备份。
7. 标记发布提交，记录数据库变更和回退步骤；确认目标环境后再提审、发布。数据库结构发生变化时，不能只回滚前端代码。
