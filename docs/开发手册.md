**一分钟理解这套架构**：小程序端**不能**直接读写数据库，所有请求都走同一个云函数 `api`，由 `service.js` 里的一段段 `if (action === 'xxx')` 分发。这样权限校验只在服务端做一次，前端改不动它。

## 三、一次请求的完整链路

以首页点「发消息给门店」为例：

```
home/index.wxml   bindtap="contact"
  → home/index.js   contact()  →  api.call('chat.open')
    → utils/api.js   wx.cloud.callFunction({ name:'api', action, data, token })
      → cloudfunctions/api/index.js   service(event, { openid })
        → service.js   handle(): actor() 校验身份 → 业务逻辑 → repo.put()
          → 云数据库
        ← 返回 { ok:true, data:... }
```

记住两件事：

1. **`token` 自动带**，不用你操心。`utils/api.js` 从 storage 里取 `session` 塞进去。
2. **报错统一是 `throw`**，代码 `AUTH` 会自动跳回登录页。

## 四、增删改查通用公式

这套项目里加任何一个功能，都是固定的 4 步：

```
① 数据库：确认集合存在（database/collections.json）
② 后端：在 service.js 里加一个 action，做完参数校验 + 权限校验
③ 前端：页面里 api.call('你的action', 参数)，setData 到 data
④ 测试：在 tests/service.test.js 里加一个用例，跑 npm test
```

**顺序不能反。** 先想清楚"数据长什么样、谁能读谁能写"，再写代码。反过来做，权限一定漏。

## 五、完整实例：管理后台的「服务管理」

这是我给你做的第一个功能，直接对着真实代码看。需求：管理员能新增 / 查看 / 修改 / 删除首页展示的服务卡片。

### ① 数据库

集合 `services` 已经在 `database/collections.json` 里了，字段是 `name / category / description / enabled / createdAt`。**没有新建集合这一步**——先查，别急着建。

### ② 后端（`cloudfunctions/api/service.js`）

**查**（读全部，包括停用的）：

```js
if (action === 'admin.services') { admin(user); return { items: await repo.list('services', {}, { order: 'createdAt', limit: 100 }) }; }
```

**增 / 改**（同一个 action，`data.id` 有值就是改，没值就是增）：

```js
if (action === 'admin.serviceSave') return repo.transaction(async tx => {
  const fresh = await actor(ctx, event.token, tx); admin(fresh);          // 1. 身份 + 权限
  const name = text(data.name, 40, '服务名称');                            // 2. 参数校验
  need(Object.keys(CATEGORIES).includes(data.category), 'INVALID', '请选择服务类别');
  const description = text(data.description, 60, '服务说明');
  need(typeof data.enabled === 'boolean', 'INVALID', '服务状态无效');
  const id = data.id ? text(data.id, 32, '服务编号') : crypto.randomBytes(12).toString('hex');
  const old = await tx.get('services', id);
  need(!data.id || old, 'INVALID', '服务不存在或已被删除');                  // 3. 改之前先确认存在
  await tx.put('services', id, { name, category: data.category, description, enabled: data.enabled, createdAt: old?.createdAt || clock(), updatedAt: clock() });
  await audit(tx, fresh, 'service.save', id, { name, category: data.category, enabled: data.enabled });  // 4. 记审计
  return { id };
});
```

**删**：

```js
if (action === 'admin.serviceDelete') return repo.transaction(async tx => {
  const fresh = await actor(ctx, event.token, tx); admin(fresh);
  const id = text(data.id, 32, '服务编号');
  need(await tx.get('services', id), 'INVALID', '服务不存在或已被删除');
  await tx.remove('services', id);
  await audit(tx, fresh, 'service.delete', id, {});
  return {};
});
```

**四条硬规矩**（照做就不会出安全问题）：

1. **写操作一律包在 `repo.transaction()` 里**。`tx` 是事务版 repo，出错自动回滚。
2. **权限靠 `actor()` 拿到的服务端身份判断**，永远不信前端传来的 `role`。`admin(user)` / `staff(user)` 是现成的断言。
3. **所有外部输入过 `text()` 校验**：非空、长度上限。没校验的参数就是漏洞。
4. **每次写操作都 `audit()`**，管理后台的每一步都要留痕。

另外 `repo.remove()` 是新加的方法，定义在 `index.js` 的 `repository()` 里——**数据库的所有访问都必须经过这个出口**，不要在别处直接 `db.collection()`。

### ③ 前端（`miniprogram/pages/admin/index.js` + `.wxml`）

JS 部分只有四件事：

```js
// 1) data 里加字段
services:[], serviceId:'', serviceName:'', serviceDesc:'', serviceEnabled:true,
editingService:false, categoryOptions:Object.values(categories), categoryKeys:Object.keys(categories), categoryIndex:0

// 2) load() 里加一个分支，把数据取回来
else if(this.data.tab==='services'){const r=await api.call('admin.services');this.setData({services:r.items,more:false});}

// 3) 编辑：把被点的这条记录填进表单
editService(e){const s=this.data.services.find(x=>x._id===e.currentTarget.dataset.id);this.setData({serviceId:s._id,serviceName:s.name,...});}

// 4) 保存 / 删除
async saveService(){ ... await api.call('admin.serviceSave',{id:this.data.serviceId,name,description,category:...,enabled:...}); }
async removeService(e){ ... await api.call('admin.serviceDelete',{id}); }
```

WXML 部分就是加一个 tab 按钮 + 一个 `<block wx:if="{{tab === 'services'}}">` 区块，复用页面里已有的 `card / field / label / row` 样式类，不用新写 CSS。

**表单可以直接用 `data-key` 复用已有的 `input` 处理器**，不用给每个输入框写一个函数：

```html
<input class="field" value="{{serviceName}}" data-key="serviceName" bindinput="input" maxlength="40"/>
```

### ④ 测试（`tests/service.test.js`）

```js
test('admin manages the service catalog; customers cannot write and changes are audited',async()=>{
  // 客户无权 → FORBIDDEN；参数非法 → INVALID；改不存在的 → INVALID
  // 增了之后客户能查到；停用后客户查不到；删了之后再删 → INVALID
  // 最后断言审计日志里有 service.save 和 service.delete
});
```

**测试要先写"不该成功"的用例，再写"该成功"的。** 权限漏洞都是这么被发现的。

> 这次真实踩到的坑：我第一版测试用了空身份调 `services.list`，跑出来 `AUTH` 失败。原因是这个接口是**需要登录**的。这就是为什么必须跑测试——不跑就得上线后才发现。

## 六、验证三件套

改完代码，按顺序跑：

```bash
npm test      # 21 个单元测试，覆盖权限、幂等、事务回滚
npm run check # JSON、JS 语法、8 个页面四件套是否齐全、WXML 里有没有写错标签
              # 然后打开开发者工具，模拟器点一遍
```

`npm run check` 特别有用：它能抓出"加了新页面但忘了建 .wxss""app.json 里写了不存在的页面"这类错误。

**加新页面的完整动作**（比如加一个"服务详情页"）：

1. 建 `miniprogram/pages/service/index.js / .json / .wxml / .wxss` 四个文件
2. 在 `app.json` 的 `pages` 数组里加 `"pages/service/index"`
3. 跑 `npm run check` 确认页面成组
4. 跳转用 `wx.navigateTo({url:'/pages/service/index?id=xxx'})`

### 不依赖账号也能开发：本地演示模式

`miniprogram/config.js` 里有个开关：

```js
mock: true    // 所有接口走 miniprogram/mock/ 的内存假数据，不需要 AppID / 云环境 / 手机号能力
mock: false   // 接口走真实云函数
```

- 切换点只有 `utils/api.js` 一处，**页面代码不受影响**。
- 演示数据在内存里，重启小程序即恢复初始状态。
- 登录页在演示模式下会多出「以客户 / 以门店 / 以管理员进入」三个按钮。
- `tests/mock.test.js` 保证这一层不会被改坏，`npm test` 会带上它。
- ⚠️ 联调真实云函数或提交审核前必须改回 `false`，同时把 `cloudEnv` 填上真实环境 ID。具体步骤（建集合、建索引、部署云函数、导种子数据、设管理员）见 `docs/环境切换清单.md`。

### 接真云环境后的登录：开发期登录开关（devLogin）

个人主体小程序没有微信「获取手机号」能力，所以 `mock: false` 接上真环境后，登录页的手机号按钮依然走不通。为此准备了第二个开关：

```js
// miniprogram/config.js
mock: false,      // 走真实云函数
devLogin: true,   // 登录页出现「开发登录」入口，用测试手机号注册/登录
```

- **判断在服务端**：云函数 `api` 的环境变量 `DEV_LOGIN=1` 时才接受 `dev:<手机号>` 凭证；生产环境不设该变量，此分支永远不执行。前端开关只控制入口显示。
- 安全边界：只跳过手机号验证这一步，格式校验、一机一号绑定、角色分配全部照常；**前端无法指定角色**。由 `tests/service.test.js` 的 "dev login switch" 用例守住。
- 三个开关的关系：`mock` 优先于 `devLogin`；两者不要同时开；上线前两者都必须是 `false`。
- 完整用法（含管理员 openid 怎么拿、门店身份怎么来）见 `docs/环境切换清单.md` 第 4 节。

## 七、和 AI 协作的规矩

### 下指令的模板

```
【目标】管理后台加一个"服务管理"tab，能增删改查首页展示的服务卡片
【已有的】services 集合已存在，字段 name/category/description/enabled
【约束】按项目现有风格：写操作包事务、权限用 admin(user)、输入过 text() 校验、写操作记 audit
【验收】npm test 全过，npm run check 全过
【别动】不要改 project.config.json 的 appid，不要碰支付相关代码
```

四个要素：**目标 / 已有条件 / 约束 / 别动什么**。少了"别动什么"，AI 很容易顺手把不相干的文件也改了。

### 三条铁律

1. **每次让 AI 改完，必须跑 `npm test`。** 现在的代码是能跑的、有 21 个测试保护的，这是你最大的资产，别让它在无人验证的改动里悄悄坏掉。
2. **让 AI 一次只做一件事。** 一口气要 5 个功能，出错了你根本不知道是哪一步坏的。
3. **改完就 `git commit`。** 一次提交对应一件事，坏了好回退。

```bash
git status                      # 看改了哪些文件
git add -A
git commit -m "feat: 管理后台新增服务管理"
git push                        # 推到 GitHub，同学能看到
git log --oneline               # 看历史
```

想撤销某个文件的改动：`git checkout -- 文件名`。
